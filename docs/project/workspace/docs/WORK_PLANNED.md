## Assignment Handover Implementation Guardrails

- New work creation belongs to generated management accounts only: `mu_*` or `ml_*`.
- Assignment create starts by selecting unit(s); selected units resolve to their generated `mu_*`
  assignees by default.
- The handover requester is the current lane holder, not the work creator or
  `WorkAssignment.CreatedByUserId`: `authenticatedUserId == fromAssigneeUserId`.
- Handover request creation must not execute runtime ownership changes.
- The target recipient must approve/reject the handover request in `Công việc cần thực hiện`.
- Runtime handover executes only after approval and must record request id, requester, and
  approving recipient in history/action context.
- Handover is one assignment at a time; do not cascade to children or a whole work subtree.
- Replace exactly one `fromAssigneeUserId -> toAssigneeUserId` lane and keep other assignees
  unchanged.
- Valid first transitions:
  - `mu -> normal user` in the same unit
  - `normal user -> normal user` in the same unit
  - `normal user -> mu` in the same unit
  - `mu -> mu` for cross-unit transfer after return to unit manager
- Cross-unit normal-user movement is not direct: normal user returns to same-unit `mu`, source `mu`
  hands to target `mu`, then target `mu` can hand to a normal user in that unit.
- Block target collisions when the target already has an active lane, binding, period, report, or
  queue row for the same assignment/template/period identity.
- Preserve `WorkAssignment.CreatedByUserId`, `WorkTemplateAssignee.CreatedByUserId`,
  report/period creators, submitter, approver, returner, and historical report log actors.
- Rebuild affected DocRole/list projections after source writes so old owner loses active access
  and the new owner sees the existing report lane.
- If a post-source DocRole list projection rebuild fails, the resilient projection wrapper enqueues a
  scoped retry job; this is eventual-sync insurance, not a transaction or broad auto repair.
